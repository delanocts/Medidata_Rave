Operator guide

Rave Test Data Pipeline

A configuration-driven pipeline that reads a Medidata Rave study's design, generates clinically plausible data for it with an LLM, loads that data through RWS, and reports what actually landed. Pointing it at a different study means writing one config file.

The tool exists because populating a Rave study by hand is slow and populating it with junk is useless. It reads the study's own metadata to learn every folder, form, field, codelist and range, generates values that conform to all of them, and then proves what it wrote by reading the subject back out of Rave.

Nothing about a specific study lives in the code. The engine, the skills and the defaults are fixed; a study file supplies the host, the study name, the site and a few generation preferences.

If you have just cloned the repository, start with Getting started from a fresh clone below and come back to the pipeline diagram once it runs.

Getting started from a fresh clone

Five steps from an empty folder to a populated subject. The fourth one — the ALS workbook — is the only part the tool cannot fetch for you.

You needWhy
Python 3.11 or newer Built and tested on 3.14.
A Rave account with RWS access Basic auth. MFA must be off, so this is normally a service account. It needs the Architect role to read study design.
An Anthropic API key with billing Generation calls the Claude API. A key on a zero-balance account authenticates and then fails at the first form.
A non-production study Dev, Sandbox, UAT or Training. Production is refused and no flag unblocks it.

  1. Clone the repository

    The tool lives in the rave-testdata-agent subfolder — every command below assumes you are inside it. 

    git clone https://github.com/TechDlx/Medidata_Rave.git
cd Medidata_Rave/rave-testdata-agent

  2. Create a virtualenv and install the dependencies

    Use a virtualenv rather than a global Python. Several installs of the same version can coexist, and installing into one while your editor runs another produces ModuleNotFoundError from a checkout where everything is in fact present. 

    # Windows
python -m venv .venv
.venv\Scripts\activate

# macOS / Linux
python3 -m venv .venv
source .venv/bin/activate

pip install -r requirements.txt

    In VS Code, run Python: Select Interpreter and choose .venv. If a script still cannot find its imports, it will tell you which interpreter is running and how to fix it rather than throwing a bare traceback.

  3. Create your .env

    Copy the committed template and fill in three values. The file is git-ignored and must never be committed; nothing else in the tool reads credentials, and they are registered for redaction the moment they load. 

    # Windows
copy .env.example .env

# macOS / Linux
cp .env.example .env
    # .env
RAVE_USERNAME=your.rave.login
RAVE_PASSWORD=your-rave-password
ANTHROPIC_API_KEY=sk-ant-...

  4. Create or update the study configuration

    One file per study in config/studies/. Its filename minus the extension is what you pass to --study, so onc-114.yaml becomes --study onc-114. The repository ships aes-002.yaml as a worked example — copy it rather than starting from blank. 

    # Windows
copy config\studies\aes-002.yaml config\studies\onc-114.yaml

# macOS / Linux
cp config/studies/aes-002.yaml config/studies/onc-114.yaml

    Only these keys have to be set. Everything else falls back to config/defaults.yaml, which is shared by every study and should not carry study-specific values.

    KeySet it to
    rave.base_url Your Rave host, https, no trailing slash.
    rave.environment DEV, Sandbox, UAT or Training. Anything resembling production is refused.
    study.name Exactly as Rave lists it. A1 prints the studies your account can see if you are unsure.
    site.number The ODM Location/@OID — not the site label. See the warning below.
    subjects.count How many subjects to end up with. With the default on_existing_id: skip this is a ceiling, not a batch size.
    subjects.id_prefix Prefix for generated IDs, padded by id_pad_width. Match any mask the study enforces.
    generation.therapeutic_area The indication, in plain words. This is what makes the data clinically apt rather than merely valid. 
    # config/studies/onc-114.yaml
rave:
  base_url: "https://yourhost.mdsol.com"
  environment: "UAT"                # must be non-production

study:
  name: "ONC-114"                   # exactly as Rave lists it

site:
  number: "20431"                   # the ODM Location OID
  name: "UAT-ONC-114"               # the label, for reporting only
  create_if_missing: false          # see note

subjects:
  count: 2
  id_prefix: "TST-"
  id_start_number: 1
  id_pad_width: 3                   # -> TST-001, TST-002

generation:
  therapeutic_area: "Metastatic colorectal carcinoma, second line"
  therapeutic_realism: true

dynamics:
  enabled: true
  trigger_strategy: "maximize"
    site.number is the OID, not the label

    Rave's site number is the ODM Location/@OID; the name is only a label, and local conventions can make the two look reversed — a site displayed as UAT-ONC-114 may well have OID 20431. Every SiteRef the tool writes carries the OID, so getting this wrong sends data to the wrong site or nowhere. A1 and A2 both list the sites they can see; follow the pattern of the existing ones.

    Leave create_if_missing: false unless you know the account can write administrative data. Most data-entry service accounts cannot, and Rave reports that missing permission as Study does not exist — which reads exactly like a typo. Creating the site in the Rave UI is usually the faster route.

    Config is validated at startup against a schema, and every problem is reported at once rather than one per run. To check the file without touching Rave: 

    python scripts/run_metadata.py --study onc-114 --dry-run

  5. Confirm access

    With credentials and config both in place, this proves the whole chain: DNS, TLS, authentication, that the study is visible to your account, that the site exists, and that the Anthropic key works. 

    python scripts/test_connection.py --study onc-114

    Every mandatory check must pass. Two results deserve a second look even though they are only warnings: Architect metadata access failing means the account cannot read study design, and Edit checks in metadata reporting zero means the next step is the only route to this study's dynamics.

  6. Download the ALS from Rave and drop it in

    RWS returns study structure but not edit checks, and drafts can be listed but not downloaded. The ALS workbook is the only source for the logic that drives dynamic folders and forms, and it has to be exported by hand.

    In Rave Architect: open the study, select the draft matching the CRF version you are targeting, and use Download Draft, choosing the Excel / ALS format. run_metadata.py prints the available draft names and OIDs, so run it once first — it also creates the folder the file goes into: 

    python scripts/run_metadata.py --study onc-114

    Then put the workbook here, named however Rave exported it:

    output/ONC-114/metadata/ONC-114_3.xls
       └───┬───┘
   your study.name from the config

    Re-run run_metadata.py and the als row changes from missing to manual. Any .xls, .xlsx or .xlsm in that folder is picked up automatically.

    The .xls is not a spreadsheet

    Architect exports SpreadsheetML — XML with a .xls name. Opening and re-saving it in Excel can convert it to a real binary workbook, which the parser cannot read. Move the downloaded file without opening it.

    Without an ALS the pipeline still runs. It fills the seed folders and discovers dynamics by attempting writes, but it cannot predict them and cannot report predicted against actual.

  7. Dry run, then go live

    The dry run builds every payload and posts none of them, so you can check the site resolves and the subject IDs are what you expect before anything reaches Rave. 

    python scripts/run_all.py --study onc-114 --dry-run
python scripts/run_all.py --study onc-114

    Expect the better part of an hour for the first subject on a mid-size study; almost all of it is Rave answering one POST at a time. Subjects are independent, so raise execution.max_parallel_subjects and ten of them cost close to what one costs — the request budget in rave.requests_per_minute is divided between them, so the load on Rave does not rise with it. The report lands in output/<STUDY>/reports/ as JSON and HTML.

What the clone does not include

.env, .venv/ and output/ are all git-ignored, so a fresh clone has no credentials, no dependencies and no run artifacts. That is deliberate: it means no one can commit a credential or another study's clinical data by accident.

How the pipeline works

Six stages run in order. Three of them cross into Rave; the rest read and write local artifacts. Each stage hands the next one a file on disk, which is what lets any stage run on its own.

StageScriptRaveWhat it does
A1 test_connection.py reads Proves DNS, TLS, credentials, study visibility, design-metadata access, the site, and the LLM key. Exits non-zero on any mandatory failure.
A2 run_metadata.py reads Downloads ODM metadata, the matrix map, sites and subjects. Skips anything already cached and unchanged. Picks up a hand-exported ALS if present.
A3 run_model.py offline Turns metadata plus the ALS into the normalized study model and the dynamics graph. Makes no network calls at all.
A4 run_provision.py writes Confirms the site, allocates subject IDs from the prefix, and creates the subjects that do not yet exist.
A5 run_generate.py offline Asks the LLM for values, checks every one against the metadata, and repairs what fails. Caches results so a re-run costs nothing.
A6 run_submit.py writes Assembles ODM and posts it, one form per request so a rejection names the form that caused it.
A8 run_dynamics.py writes Drives A5 and A6 in passes, unlocking dynamic folders as trigger values land. This is the stage a full run actually uses.
A7 run_verify.py reads Reads each subject back and compares field by field, then writes the run report as JSON and HTML.

How agents, skills and scripts connect

Three layers, and they are deliberately unequal. The scripts are thin, the modules hold every decision, and the skills hold what the project has learned about Rave. Two of those skill files are read by the running tool, not only by a person.

The scripts are deliberately thin

A script parses flags, loads the config and the secrets, builds one agent, and prints a summary. No study logic lives in scripts/ at all. That is what makes every stage runnable on its own, and it is why run_all.py can be little more than an ordered list — the stage table in orchestrator.py, which also records which stages write to Rave and which run once per subject.

The modules are the agents

One package per concern, and the boundaries are load-bearing. Everything that speaks to Rave goes through rave/client.py, so retry, rate limiting and credential redaction cannot be bypassed by a caller that forgets. Everything the model produces goes through generation/validators.py before it can be submitted, so a value is never trusted because the model sounded confident.

Two skills are read at run time

Most of the thirteen skills are written for a person, or for a Claude Code subagent working on this repository. Two are read by the running process itself — one through generation/skill_rules.py, the other by the submitter directly — which means editing a Markdown file changes what the tool does with no code change:

Skill fileRead byEditing it changes
clinical-data-generation/reference/data-rules.md prompt_builder.py The rules handed to the model in every generation prompt — coded values over labels, date handling, clinical plausibility, and the ban on real personal data.
rave-submission/reference/error-codes.md submission/rejections.py How a Rave rejection is classified — and so whether the dynamics loop reads it as a dead folder, a missing form, or something to retry smaller.
Degrades safely

A missing skill file falls back to a built-in default rather than failing. The pipeline still runs from a checkout with no .claude/ directory at all. You lose the editable rules, not the tool.

Where a new lesson goes

When you learn something about Rave that the code had to work around, it belongs in the skill for that activity rather than in a comment beside the fix. The skills are why a second study did not have to repeat the first one's discoveries, and the two files above are why some of those lessons take effect without anyone editing Python.

The dynamics loop

Most of a study is not visible to a new subject. Folders arrive only when an edit check fires, and the obvious way to detect that does not work.

Rave's clinical dataset returns only folders that already hold data, so a folder that is active but empty is invisible — which is exactly the state you are trying to detect. The loop therefore uses the write itself as the detector: if Rave accepts data for a folder, that folder is live.

Running it

With the virtualenv active, one command runs everything. The orchestrator records each stage's outcome in run_manifest.json, which is what --resume reads. 

python scripts/run_all.py --study aes-002              # everything, in order
python scripts/run_all.py --study aes-002 --dry-run    # build payloads, post nothing
python scripts/run_all.py --study aes-002 --resume     # continue after a failure
python scripts/run_all.py --study aes-002 --stop-after model
Resume is for failures only

--resume skips every stage already marked ok in run_manifest.json — provisioning included. Use it to carry on after something broke, never to add a subject, or the new subject is never created.

Adding a subject to a study already running

Raise subjects.count and run the pipeline. With the default on_existing_id: skip, count is a ceiling: setting it to 3 when TST-001 and TST-002 exist creates only TST-003. Switch to continue_numbering if you would rather count meant "this many new ones".

To touch only the new subject rather than revisiting the others:

python scripts/run_provision.py --study aes-002
python scripts/run_dynamics.py  --study aes-002 --subject TST-003
python scripts/run_verify.py    --study aes-002

Running it from a browser

A local console: every configurable field as a form, and a run you can watch. It needs nothing beyond requirements.txt — it is built on the standard library. It is a viewer rather than a second way to run things: it shells out to run_all.py and reads the same artifacts, so the command line stays the single execution path and --resume still works if you close the tab. 

python web/server.py            # then open http://127.0.0.1:8765

It binds to 127.0.0.1 because the process holds a session that can write to Rave, and it never sends credentials to the browser — the page is told whether .env loads and nothing more.

Where the study list comes from

The dropdown is simply the .yaml files in config/studies/. There is no registry and no database: drop a file in that folder and it appears. What it lists is the file name, not the study name inside the file — the same token run_all.py --study takes.

FileThe dropdown showsstudy.name inside
config/studies/aes-001.yamlaes-001AES-001
config/studies/aes-002.yamlaes-002AES-002

Selecting one runs the real loader — defaults.yaml merged under the study file, plus any RAVE_AGENT_* overrides — and fills the form with the effective values. A field your study file never mentions shows the default rather than sitting blank, so what you read is what a run would use.

Step by step

  1. Pick a study, or create one

    Choose from the dropdown, or type a name and press Create. Create only adds the option in the browser — nothing is written until you save. A new study starts from the defaults, so the Rave URL, environment, study name and site are all yours to fill in before it will validate.

  2. Edit the fields

    Seven groups: Rave, Study, Site, Subjects, Generation, Dynamics, and metadata and execution. Each carries help text where the reason is not obvious. The edits you will make most often are the subject count, prefix and start number, and execution.max_parallel_subjects.

  3. Save

    Save configuration writes config/studies/<name>.yaml — but only after the real loader accepts it. A rejected configuration lists its actual problems and leaves the existing file untouched, so a bad edit cannot overwrite a working study. Only values that differ from the defaults are written, which keeps the file the short statement of what makes this study different.

  4. Decide how the run should behave

    Dry run is on by default: every payload is built and nothing is posted. Note that it also short-circuits the connection and metadata stages, so it proves the configuration rather than the connection — use Stop after → connection, live, for that. Resume skips stages already marked ok. Stop after ends the run at a chosen stage; stopping after the study model is the quick way to check a configuration without touching Rave.

  5. Start, and watch

    Unchecking Dry run reveals a warning first, because that writes subjects and clinical data into Rave. Once running, the Stages panel fills in as each one completes, with its duration and any failure detail, and the Output panel streams the same text the terminal would show. Both come from a snapshot pushed once a second, so a refresh mid-run picks up correctly rather than losing its place. Open last report appears as soon as a report exists.

Saving rewrites the file

Going through the form discards comments and any key left at its default. The result is valid and means the same thing, but the notes are gone. If a study file carries reasoning worth keeping — why that site number, where a value was confirmed — edit it by hand instead.

Three things that will surprise you

One run at a time. Two runs against one study would race run_manifest.json and the activation state, which assume a study has a single owner.

The console only sees runs it started. Launch run_all.py in a terminal and the page will not show it.

The dropdown does not refresh itself. A file added to config/studies/ while the page is open needs a browser reload; only saving re-fetches the list.

Using it for a different study

One new file. The engine, the skills and the shared defaults are the same for every study; the study file supplies only what is genuinely study-specific.

What to check on a study nobody has run before

The procedure is the same as Getting started above — write the config, prove access, add the ALS, dry run, go live. What changes is how carefully you read A3's output before committing to a long run.

Read the model warnings

run_model.py is offline and takes seconds, so run it and read what it says before spending an hour of generation. Three numbers tell you what the run can reach:

WarningWhat it means for the run
Form assignments by source How much of the structure came from the ALS versus was inferred by sampling existing subjects. Inferred assignments prove a form can appear in a folder, not that it is there at baseline.
Folders with no form assignments Nothing can be written to them. Usually means the ALS is missing, or those folders genuinely hold no forms.
Most powerful trigger fields The report lists which field values unlock the most. Most studies have one eligibility or enrolment flag that opens the bulk of the visit schedule; if that list is empty, dynamics will be discovered by trial rather than predicted.

Each study needs its own ALS

Nothing carries over between studies. A study whose ALS you have not exported will populate its seed folders and stop there, which looks like success until you read the coverage fraction in the report.

Custom functions need declaring

If A3 reports unresolvable custom-function checks and the folders they drive matter to you, read the function source — the ALS carries it — and declare its effect under dynamics.custom_function_overrides in the study file. Until then those targets are reported as unreachable rather than silently dropped.

Some limits are discovered, not declared

Rave enforces a maximum number of log records per form that appears in neither the metadata nor the ALS. The tool finds it by being refused, shrinks the record list, and caches what worked in model/log_limits.json — so the first run on a new study does more retrying than later ones. That file is per study and safe to delete if the design changes.

Reading the report

The report is built from what Rave returns, not from what the tool believes it sent. Those two disagree more often than you would expect.

VerdictMeaningAction
match Stored exactly as sent. None.
normalised Rave reshaped it and kept the meaning — text upper-cased, a datetime re-spelled to full ISO, a decimal padded to the field's precision. None. This is Rave being Rave.
narrowed The field is smaller than the value; a year-only date keeps the year. None, but worth knowing which fields do it.
absent Generated and sent, but Rave does not hold it — that form's submission was refused. Check the rejection in state/; usually a folder or form that never activated.
mismatch Rave holds something different. Rare, and always interesting. Investigate. It usually means an undeclared derivation or a field mask.

The report also lists every folder the dynamics graph predicted that never accepted data. Silence there would be the real failure: a study can look fully populated while a third of it was never reachable.

What the tool cannot do for you

Edit checks are not in RWS

The metadata endpoint returns structure only, and drafts can be listed but not downloaded. Dynamics come from a hand-exported ALS or they are discovered empirically. Architect exports that workbook as SpreadsheetML — it is XML despite the .xls name, so no spreadsheet library is involved.

Custom functions are opaque

A check whose action is a custom function can be detected and named, but its logic is not derivable from any export. Declare its effect under dynamics.custom_function_overrides once you know it; until then it is reported as unresolvable rather than silently dropped.

Derived fields belong to Rave

Rave computes them and refuses any value you send. They are excluded from generation and the exclusion is reported, so the field count in the report is writable fields, not all fields.

Some things need a person

Creating a site needs administrative-data write permission, which a data-entry service account usually lacks — and Rave reports that missing permission as Study does not exist, which reads exactly like a typo. If clinical writes to the same study succeed while the site POST fails, it is access, not naming.

Safety

Production is refused twice: the config loader rejects any environment matching a production pattern regardless of the allow-list, and a pre-tool hook blocks a hand-written command that would bypass the loader. No configuration flag unblocks either.

TLS verification cannot be disabled. Credentials come from .env, are registered for redaction the moment they load, and never reach logs, reports, prompts or output. Every request and response is archived for audit, and all generated data is synthetic and marked as such in the report.
